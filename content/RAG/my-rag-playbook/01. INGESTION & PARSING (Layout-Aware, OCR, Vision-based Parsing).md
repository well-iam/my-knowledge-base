### 1. 🎯 Obiettivo dello Stage

**L'ingestione e il parsing dei dati rappresentano le fondamenta assolute di qualsiasi sistema RAG di produzione.** Questo stage si occupa dell'estrazione del testo grezzo e della struttura dai file sorgente prima di qualsiasi altra operazione di elaborazione o chunking. Il problema architetturale primario che risolve è la **trasformazione di dati destrutturati e multiformato (come PDF, documentazione Markdown, pagine web o codice sorgente) in un formato plain text standardizzato e pulito che l'LLM e i modelli di embedding possono comprendere ed elaborare in modo efficiente.** Un parsing inadeguato o approssimativo introduce rumore visivo, distorsioni semantiche e perdita di contesto strutturale, degradando l'intera pipeline di ricerca e generazione secondo il principio ingegneristico del _"Garbage In, Garbage Out"_.

> [!NOTE] La qualità dell'ingestione influisce direttamente sulle prestazioni del RAG: un indice ben organizzato è paragonabile a una biblioteca catalogata con precisione, dove il recupero delle informazioni è rapido e mirato.

### 2. 🧠 Analisi Tecnica delle Tecniche
Ci sono 6 tecniche:
#### 1. Naive Parsing

- **Come funziona**: Estrae il testo in modo lineare e "piatto" da file digitali non strutturati (come PDF o TXT) senza tenere conto della disposizione spaziale degli elementi, dell'impaginazione o della formattazione gerarchica.
- **Pro & Contro**:
    - _Pro_: Estremamente veloce, a bassissimo costo computazionale, facile da implementare e con zero overhead di manutenzione.
    - _Contro_: Causa una grave perdita di contesto strutturale; distrugge la formattazione di tabelle, intestazioni e flussi di lettura multi-colonna, inserendo righe di testo spezzate o incoerenti che compromettono la qualità del retrieval.
- **Parametri Chiave**: Non prevede parametri di configurazione strutturale; le metriche si limitano al conteggio dei token grezzi generati.

#### 2. Layout-Aware Parsing

- **Come funziona**: Riconosce e preserva attivamente la struttura visiva e la gerarchia del documento (come titoli, colonne, tabelle e blocchi logici), convertendola in formati strutturati come Markdown o HTML.
- **Pro & Contro**:
    - _Pro_: Mantiene la coerenza del flusso di lettura dei documenti complessi e conserva le gerarchie del testo (es. relazioni titolo-paragrafo), migliorando la precisione del retrieval semantico.
    - _Contro_: Incrementa notevolmente la latenza e i costi di elaborazione rispetto al parsing nativo.
- **Parametri Chiave**: Richiede l'integrazione di strumenti esterni. Le fonti menzionano librerie leader come **Unstructured** (per PDF, Word e HTML), **Firecrawl** (ottimizzato per web scraping e conversioni di siti web), **Multi-on** (automazione AI), e servizi cloud enterprise come **AWS Textract** e **Azure Document Intelligence**.

#### 3. OCR & Vision-based Parsing

- **Come funziona**: Impiega modelli di visione profonda per interpretare direttamente PDF scansionati, layout grafici complessi o impaginazioni visive senza dover convertire preventivamente il documento in testo puro.
- **Pro & Contro**:
    - _Pro_: Rappresenta l'unica soluzione efficace per documenti cartacei digitalizzati o PDF non nativi dove il testo non è estraibile programmaticamente.
    - _Contro_: Altissimo consumo di risorse di calcolo (richiede GPU), latenza di esecuzione molto elevata e rischio di errori di interpretazione visiva.
- **Parametri Chiave**: Modelli di riferimento citati nelle fonti: **ColPali** e **Donut**.

#### 4. Table Extraction

- **Come funziona**: Identifica e isola in modo mirato le tabelle all'interno dei documenti, formattandole in Markdown, HTML o generando riassunti descrittivi sintetici prima di indicizzarle.
- **Pro & Contro**:
    - _Pro_: Impedisce la frammentazione lineare dei dati tabulari (che renderebbe incomprensibili le relazioni riga-colonna per l'LLM), salvaguardando l'accuratezza dei dati strutturati.
    - _Contro_: Elevata complessità di gestione dei bordi, delle righe unite o di layout tabulari complessi, che possono portare a formattazioni errate.
- **Parametri Chiave**: Conversione mirata in strutture **HTML** o **Markdown** per mantenere intatta la semantica relazionale.

#### 5. Custom & Tailored Parsing (Caso di Studio Wandbot)

- **Come funziona**: Sviluppo di una pipeline di parsing proprietaria e altamente personalizzata in base alla tipologia specifica di file sorgente per ottimizzare la precisione del dominio.
- **Pro & Contro**:
    - _Pro_: Massima accuratezza; preserva perfettamente la struttura logica del codice e della documentazione, azzerando le allucinazioni causate da un'ingestione errata.
    - _Contro_: Richiede un notevole sforzo di sviluppo software iniziale e ha una scarsa flessibilità per formati differenti da quelli previsti.
- **Parametri Chiave (tecniche usate in Wandbot)**:
    - **Custom Markdown Parser**: Sviluppato per mantenere la struttura gerarchica delle intestazioni, sezioni e blocchi di codice.
    - **NBConvert**: Utilizzato per convertire i Jupyter Notebook (`.ipynb`) in Markdown prima di passarli al parser proprietario.
    - **Concrete Syntax Trees (CST)**: Utilizzato per analizzare il codice sorgente, garantendo che le definizioni di funzioni e i blocchi logici restino intatti all'interno del chunk.

#### 6. Text Preprocessing & Tokenization-Safe Cleaning

- **Come funziona**:
    - **Preprocessing Markdown (Beautiful Soup)**: Conversione preliminare del Markdown in HTML e successivo parsing tramite Beautiful Soup (`convert_contents_to_text`) per rimuovere tag di immagini, link e formattazioni irrilevanti, isolando il plain text pulito.
    - **Cleaning Special Tokens (`make_text_tokenization_safe`)**: Rimozione programmata di caratteri speciali e delimitatori proprietari (es. token speciali del modello) per evitare la _"vocabulary pollution"_ e anomalie durante la tokenizzazione.
    - **Allineamento del Tokenizer**: Calcolo delle lunghezze dei documenti usando il tokenizer specifico del modello finale (es. Cohere Tokenizer) anziché semplici split di parole.
- **Pro & Contro**:
    - _Pro_: Fornisce dati puliti e coerenti, previene errori distruttivi nell'LLM e consente una stima esatta delle context window e dei costi di calcolo.
    - _Contro_: Richiede uno step di computazione preliminare aggiuntivo prima dell'indicizzazione.
- **Parametri Chiave**:
    - Tokenizer: **Cohere Tokenizer** (per allinearsi a Cohere Command).
    - Metadati minimi associati: `metadata.source`, `metadata.raw_tokens` e `metadata.cleaned_tokens`.

### 3. 📊 Matrice Decisionale per la Produzione

|Tecnica|Caso d'Uso Ideale|Impatto Latenza/Costi|Rischio Principale|
|:--|:--|:--|:--|
|**Naive Parsing**|Documenti testuali semplici e piatti (.txt, PDF lineari senza colonne o tabelle) dove l'accuratezza strutturale non è critica.|**Minimo**: Elaborazione istantanea in CPU a costo zero.|**Grave perdita di contesto**: Le tabelle e i testi multi-colonna vengono destrutturati e mescolati in modo incoerente.|
|**Layout-Aware Parsing**|PDF e HTML aziendali complessi (es. report, manuali d'uso, documentazione con layout strutturato).|**Medio**: Latenza aggiuntiva introdotta dalle API di parsing; costi variabili a consumo.|**Failure visivo**: Errori di interpretazione su layout non convenzionali, con potenziale perdita di blocchi di testo importanti.|
|**OCR & Vision-based Parsing**|Archivi storici digitalizzati, scansioni cartacee, fogli di calcolo scansionati o slide ricche di infografiche complesse.|**Elevato**: Richiede elevata potenza di calcolo (GPU) o costi elevati di API esterne; latenze di runtime significative.|**Errori di trascrizione**: Possibili allucinazioni dei caratteri visivi (specialmente su testi sfocati o corsivi).|
|**Table Extraction**|Documenti ad alta densità di dati tabulari (es. bilanci finanziari, schede tecniche) dove i valori numerici sono critici.|**Medio-Alto**: Richiede algoritmi di ricostruzione strutturale o chiamate LLM dedicate per riassumere i dati tabulari.|**Disallineamento dati**: Se le colonne non vengono mappate correttamente, i valori numerici perdono il loro significato semantico nel prompt.|
|**Tailored / Custom Parsing**|Sistemi di produzione verticali con formati di dati standardizzati e di dominio specifico (es. codebase, wiki Markdown).|**Basso a runtime**: L'esecuzione di codice custom (es. CST, regex) è rapida. Richiede però un **alto costo di engineering iniziale**.|**Rigidità**: Se la struttura del file sorgente cambia improvvisamente, la pipeline di parsing si rompe e richiede modifiche al codice.|
|**Preprocessing & Cleaning**|Applicabile a qualsiasi pipeline RAG professionale prima del chunking e dell'indexing.|**Basso**: Operazioni veloci in-memory, ma essenziali per ottimizzare i token inviati all'LLM.|**Over-cleaning**: Rischio di cancellare caratteri speciali sintatticamente utili (es. operatori logici nel codice o punteggiatura critica).|

### 4. ⚠️ Divergenze & Edge Cases

Durante l'analisi del materiale del corso Weights & Biases e del relativo codice operativo, sono emersi importanti edge cases e discrepanze architetturali:

1. **Divergenza sulla Dimensione del Contesto (Token count e Chunking)**: Sotto la UI/video della lezione (Chapter 1) viene indicato l'intento didattico di usare chunk di circa **500 token senza overlap**. Tuttavia, nel codice GitHub effettivo (`Chapter01.ipynb`), l'iperparametro operativo è impostato fisicamente su `CHUNK_SIZE = 300` e `CHUNK_OVERLAP = 0`. Per un'implementazione corretta a livello di produzione, l'architetto deve considerare il codice come la fonte di verità operativa, testando la dimensione in base alla context window del modello di embedding usato (che spesso ha un limite di 512 token).
2. **Approssimazione del Calcolo dei Token (Baseline vs Produzione)**: Nel notebook baseline (Chapter 1), il calcolo del numero di token dei documenti viene eseguito tramite una semplice approssimazione basata sullo split degli spazi: `len(content.split())`. Questo approccio è insicuro in produzione poiché sottostima significativamente il reale numero di token calcolato dai tokenizer dei modelli (come quello di Cohere). Nel Chapter 3, infatti, viene corretta questa pratica introducendo l'uso del **Cohere Tokenizer ufficiale** per garantire un conteggio accurato, evitare overflow delle context window ed ottimizzare i costi computazionali delle API.
3. **Gestione dei System Prompt e delle Configurazioni**: Nei progetti RAG iniziali o di piccole dimensioni, i system prompt vengono mantenuti direttamente inline nel codice. Tuttavia, per sistemi di produzione scalabili, il corso raccomanda come best practice strutturale quella di estrarre i system prompt in file separati (TXT o JSON) per consentire il tracciamento delle versioni (version control tramite Git o W&B Weave) e facilitare la manutenzione senza modificare il codice applicativo.

### 5. 💻 Snippet / Workflow di Riferimento

Il seguente script Python mostra la corretta implementazione della pipeline di **Ingestion & Parsing** secondo le evoluzioni introdotte nei notebook del corso (integrazione di Beautiful Soup per la pulizia del layout, rimozione programmata dei token speciali e conteggio preciso dei token con il tokenizer Cohere):

```python
import re
import weave
import cohere
from bs4 import BeautifulSoup

# Inizializzazione della piattaforma di tracciamento Weave e del client Cohere
weave.init("rag-course")
cohere_client = cohere.ClientV2()

def convert_contents_to_text(raw_markdown: str) -> str:
    """
    Esegue il parsing layout-aware preliminare rimuovendo tag non testuali,
    immagini, link a immagini e formattazione irrilevante.
    """
    # Nel corso viene usato BeautifulSoup per estrarre in modo sicuro il testo
    # dopo una conversione concettuale in HTML
    soup = BeautifulSoup(raw_markdown, "html.parser")

    # Rimozione mirata di elementi non testuali (es. tag immagini)
    for img in soup.find_all("img"):
        img.decompose()

    return soup.get_text()

def make_text_tokenization_safe(text: str) -> str:
    """
    Previene la 'vocabulary pollution' e comportamenti anomali del tokenizer
    rimuovendo i token speciali proprietari del sistema.
    """
    # Sostituzione/rimozione di token speciali di sistema (es. tag speciali HTML/delimitatori)
    clean_text = re.sub(r"<\|.*?\|>", "", text)
    return clean_text

def ingest_and_parse_document(file_path: str, raw_content: str) -> dict:
    """
    Workflow completo di Ingestione, Parsing, Pulizia e Tokenizzazione Sicura.
    """
    # 1. Parsing e pulizia del layout
    parsed_text = convert_contents_to_text(raw_content)

    # 2. Pulizia dei token speciali
    safe_text = make_text_tokenization_safe(parsed_text)

    # 3. Allineamento del Tokenizer: calcolo esatto dei token reali (non tramite split())
    # Questo approccio evita overflow invisibili e gestisce accuratamente la context window
    tokens_response = cohere_client.tokenize(text=safe_text, model="command-r")
    exact_token_count = len(tokens_response.tokens)

    # 4. Restituzione del documento strutturato pronto per lo Stage 2 (Chunking)
    return {
        "content": safe_text,
        "metadata": {
            "source": file_path,
            "cleaned_tokens": exact_token_count
        }
    }

# Esempio di applicazione su un singolo file sorgente
if __name__ == "__main__":
    raw_md_doc = """
    # Guida di Setup W&B
    Benvenuto nel sistema di tracciamento. <|special_system_token|>
    ![Logo](https://wandb.ai/logo.png)
    Ecco come inizializzare un run:
    """

    documento_processato = ingest_and_parse_document(
        file_path="setup_guide.md",
        raw_content=raw_md_doc
    )

    print("Contenuto Pulito:", documento_processato["content"].strip())
    print("Metadati Associati:", documento_processato["metadata"])
```
